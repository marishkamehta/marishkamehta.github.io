_Studying LLM Behavior · Model setup_

Ollama is sufficient for many local tests. Experiments with many requests,
concurrent sessions, or repeated histories may need more control over how the
model is served. This page shows how to run the pipeline with vLLM.

Despite its name, vLLM is not a model. It is a model inference and serving
engine: software that loads a model, generates responses, and provides an API
that the pipeline can call.

The setup uses the official vLLM Docker image, one NVIDIA GPU, and
`Qwen/Qwen2.5-3B-Instruct`. The pipeline and vLLM run on the same computer, and
the API is accessible only from that computer. Configuring a separate remote
server is outside the scope of this guide. Other supported hardware requires a
different setup
([vLLM GPU installation guide](https://docs.vllm.ai/en/v0.22.1/getting_started/installation/gpu/)).

> **This page assumes that a compatible NVIDIA GPU, its driver, Docker, Docker
> Compose, and the NVIDIA Container Toolkit have already been installed.** On
> Windows, this route also requires a compatible Linux environment through WSL;
> vLLM does not run natively on Windows. Driver installation is not covered
> here because the correct procedure depends on the machine and is best handled
> by its owner or administrator.

## This setup needs Docker to reach the GPU

Before downloading a model or starting a server, open a terminal and run:

```bash
nvidia-smi
docker version
docker compose version
```

The first command should show the NVIDIA GPU and its driver. The next two should
return the installed versions of Docker and Docker Compose. Together, these
results confirm that all three are present. NVIDIA provides a separate test to
confirm that a Docker container can actually use the GPU in its
[Container Toolkit documentation](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/sample-workload.html).

If a check fails on a shared workstation or cluster, contact the person who
manages that machine before continuing. Installing or changing a driver can
affect other work running on the same system.

## The experimental design determines the server settings

The first step is to work out what the experimental design requires from the
server. This includes the expected length of the prompts and responses, how
much session history will accompany each trial, and whether several sessions
will run at the same time. These requirements determine the context length and
the amount of GPU memory the server needs.

The template keeps the server settings in `docker/.env`. From the downloaded
[`llm-blog-repo`](https://github.com/marishkamehta/llm-blog-repo) folder, create that file
from the example.

On Linux, including a Linux terminal opened through WSL:

```bash
cp docker/example.env docker/.env
```

Open `docker/.env` before continuing:

```text
VLLM_IMAGE_TAG=v0.22.1
VLLM_MODEL=Qwen/Qwen2.5-3B-Instruct
VLLM_PORT=8000
VLLM_MAX_MODEL_LEN=32768
VLLM_GPU_MEM_UTIL=0.90
HF_CACHE_DIR=./hf-cache
VLLM_API_KEY=
```

Each value controls part of the server configuration:

- `VLLM_IMAGE_TAG` selects the vLLM version. Using a numbered release prevents
  `latest` from changing the software unexpectedly.
- `VLLM_MODEL` is the Hugging Face model identifier. It determines which model
  files vLLM downloads and loads.
- `VLLM_PORT` is the local network port through which the pipeline reaches the
  server. Port `8000` serves the model API, not a graphical interface.
- `VLLM_MAX_MODEL_LEN` is the maximum combined length of the prompt and the
  generated response, measured in tokens. A longer context also requires more
  memory. vLLM documents this setting as `--max-model-len`
  ([vLLM server arguments](https://docs.vllm.ai/en/v0.22.1/cli/serve/#--max-model-len)).
- `VLLM_GPU_MEM_UTIL` sets the fraction of the selected GPU's memory available
  to this vLLM instance. `0.90` means 90 percent. Other processes still require
  memory
  ([vLLM cache configuration](https://docs.vllm.ai/en/v0.22.1/cli/serve/#--gpu-memory-utilization)).
- `HF_CACHE_DIR` is where the downloaded model files remain after the container
  stops. Keeping this directory avoids downloading the same files every time.
- `VLLM_API_KEY` is left empty because this example binds the endpoint only to
  the local computer. Authentication and encrypted transport must be configured
  before making a vLLM server reachable over a network.

The tested values may not fit every GPU. If the model cannot load, reduce the
context length or choose a model configuration suited to the available
hardware. Record any changes.

Some Hugging Face models require the user to accept access conditions and
provide a token. If a selected model is gated, set `HF_TOKEN` in the terminal
using the approved secret-management method before starting Docker. A token is
not needed merely because the model comes from Hugging Face, and it should never
be written into `.env`, a script, or version control.

## Starting vLLM downloads the model the first time

The first launch downloads both the Docker image and the model files. Later
launches can reuse those files, but the model must still be loaded into memory
before the server can accept requests. From the
[`llm-blog-repo`](https://github.com/marishkamehta/llm-blog-repo) folder, run:

```bash
docker compose --env-file docker/.env -f docker/docker-compose.yml up
```

Leave this terminal open and wait until the log says that the API server is
ready.

The Compose file starts the official `vllm/vllm-openai` image, gives it access
to one GPU, and preserves the downloaded model files. It publishes the API only
on `127.0.0.1`, so another computer cannot connect through this configuration
([official vLLM Docker guide](https://docs.vllm.ai/en/v0.22.1/deployment/docker/)).

**Prefix caching** allows vLLM to reuse work when several requests begin with
identical instructions or session history. This can help with growing
trajectories, where later trials repeat much of the earlier interaction. It
changes how the request is processed, not the prompt or response
([vLLM automatic prefix caching](https://docs.vllm.ai/en/v0.22.1/features/automatic_prefix_caching/)).

## Test the connection before sending the experiment

Keep the server running and open a second terminal. Before sending any study
materials, ask the endpoint which model it is serving:

```bash
curl http://localhost:8000/v1/models
```

If the pipeline is being accessed from Windows PowerShell, use:

```powershell
Invoke-RestMethod http://localhost:8000/v1/models
```

The response should include `Qwen/Qwen2.5-3B-Instruct`. This confirms that the
API can be reached and is reporting the expected model.

Return to the terminal environment prepared during the [pipeline
test](/blog/2026/mock-pipeline/). Open `model-registry.yaml` and confirm that it
contains:

```yaml
vllm-local:
  backend: vllm
  base_url: http://localhost:8000/v1
  served_name: Qwen/Qwen2.5-3B-Instruct
```

Then send one non-study request:

```bash
python smokes/smoke_chat.py --model vllm-local
```

A short response from `vllm-local` confirms that the pipeline can reach vLLM
and save what it returns. The behavioral demonstration tests the task itself.

The error usually indicates which part of the setup needs attention:

- a connection error points to the port or route;
- an out-of-memory error points to the model, context length, or GPU settings;
  and
- if loading stops for another reason, preserve the log before changing the
  configuration.

## The model name is only one part of the study record

Two researchers can run the same named model through different versions of
vLLM, on different GPUs, or with different context and memory settings. Those
differences may matter when the results are interpreted. Alongside the model
responses, preserve:

- the vLLM image tag and, where possible, the container-image digest;
- the Hugging Face model identifier and exact model revision or commit hash;
- the GPU model, number of GPUs, driver version, and available GPU memory;
- the context length, GPU-memory fraction, numerical precision, quantization,
  and any other server arguments;
- whether prefix caching was enabled;
- the tokenizer and chat template used by the served model;
- the sanitized registry entry, timestamps, logs, and observed errors; and
- the generation settings sent with every request.

A **revision** or **commit hash** identifies the exact snapshot of the model
files. Because those files can change without the model name changing, specify
the revision before data collection. vLLM accepts a branch, tag, or commit
([vLLM revision argument](https://docs.vllm.ai/en/v0.22.1/cli/serve/#--revision)).

## Stopping the server does not remove the downloaded model

After the smoke test or data collection has finished, return to the terminal
running vLLM and press `Ctrl+C`. Then run:

```bash
docker compose --env-file docker/.env -f docker/docker-compose.yml down
```

This removes the server container, but leaves the model files in
`docker/hf-cache`. They can be reused the next time vLLM starts.

## Ask an agent to help with the vLLM setup

After the pipeline has been downloaded, an agent can inspect the machine and
prepare this configuration. The prompt keeps system-level changes outside the
agent's authority and requires approval before it downloads files or starts a
process on the GPU.

```text
I have downloaded llm-blog-repo and want to test its vLLM Docker
route.

Work only inside this repository. Read the README, docker/docker-compose.yml,
docker/example.env, model-registry.yaml.example, and the smoke-test script before
making any change.

First inspect, but do not modify, the environment. Report:
- the operating system;
- the NVIDIA GPU model and memory shown by nvidia-smi;
- the NVIDIA driver version;
- the Docker and Docker Compose versions;
- whether Docker is configured to access the GPU;
- available disk space; and
- whether port 8000 is already in use.

Compare those findings with the model, context length, GPU-memory fraction,
cache directory, and vLLM image tag in docker/example.env. Explain unfamiliar
terms in plain language. Do not install or update a driver, Docker, the NVIDIA
Container Toolkit, CUDA, or any system package.

If the existing environment appears compatible, show me the exact files and
commands you propose to use. Estimate what will be downloaded and where it will
be stored. Wait for my approval before copying the environment file,
downloading an image or model, starting the container, or sending a request.

Keep the endpoint bound to 127.0.0.1. Do not expose a port to the network, place
a credential in a file, delete a cache, run a study, or change study materials.
After approval, start only the configured vLLM service, verify /v1/models, run
one non-study smoke request, and report the result. Save the software, model,
hardware, and server settings needed to reproduce the check, without saving any
credential.
```

A successful smoke test confirms that the pipeline can reach the model and save
its response. A behavioral experiment must also vary a condition, repeat the
procedure, and connect each response to the trial that produced it.

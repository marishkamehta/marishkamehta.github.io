_Studying LLM Behavior · Model setup_

When suitable local compute is not available, the task can remain on the local
computer while the model runs elsewhere. The pipeline sends each request to a
hosted deployment and receives the response through an API. This removes the

whose settings, limits, and safeguards become part of the study.

The instructions below connect the pipeline to an existing Azure deployment.

> **This page assumes that Azure and an approved model deployment have already
> been set up.** It does not create an Azure account, subscription, resource,
> or deployment. If these are not already available, contact the person or team
> responsible for the institution's Azure environment before continuing.

## The deployment is part of the experimental environment

In Azure, the pipeline connects to a **deployment** rather than directly to a
general model name. The deployment identifies the model made available within
an Azure resource and can also determine its version, processing location,
capacity, rate limits, and content-filter settings.

Two studies can therefore report the same general model name while using
different environments. A model update, different processing region, or
different filter can change the conditions under which responses are produced.
Reporting only “Azure” or “GPT-4” does not capture those differences.

Microsoft's current v1 documentation shows a base URL in this form:

```text
https://YOUR-RESOURCE-NAME.openai.azure.com/openai/v1/
```

The `model` field in a request contains the **deployment name**, which may not
be the same as the underlying model name
([Microsoft v1 API documentation](https://learn.microsoft.com/en-us/azure/foundry/openai/api-version-lifecycle)).
Both names belong in the study record.

## Resolve data use, filtering, and cost first

- **Data:** Confirm that the deployment may receive the study's prompts,
  stimuli, participant-derived text, and generated responses. Processing
  location can depend on whether the deployment is regional, Global, or Data
  Zone ([Microsoft data, privacy, and security
  guidance](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/openai/data-privacy)).
- **Filtering:** Azure can evaluate both prompts and completions. Record a
  blocked prompt or completion with its trial and condition rather than treat
  it as an ordinary missing response. A change to the filter during collection
  changes the experimental environment
  ([Microsoft content-filter documentation](https://learn.microsoft.com/en-us/azure/ai-studio/concepts/content-filtering)).
- **Cost and quota:** Confirm billing approval and compare the number, length,
  and concurrency of planned requests with the deployment's token and request
  limits ([Microsoft quota
  documentation](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/quota)).

## What to ask the Azure deployment owner

Before configuring the pipeline, obtain the following information from the
deployment owner:

1. **How the pipeline connects:** the complete Azure OpenAI v1 base URL and the
   deployment name used in the request's `model` field. These are the two values
   needed in `model-registry.yaml`.
2. **Which model the deployment serves:** the underlying model name and its
   version. The deployment name may be an internal label and may not identify
   either one.
3. **How the deployment operates:** its deployment type, processing region or
   data zone, authentication method, rate limits, and content-filter settings.
   These determine where requests may be processed, how the pipeline is allowed
   to connect, and what may limit or block a response.
4. **Whether it is approved for this study:** the relevant data-governance
   conditions and the billing project or cost center authorized for the calls.

Use the exact values supplied by the deployment owner. They cannot be reliably
inferred from the general model name or from the fact that the service runs on
Azure.

## Connect the pipeline without storing the credential

The pipeline supports an Azure API key stored in an environment variable. If
the institution requires Microsoft Entra ID instead, use its approved
authentication method; do not place a temporary token in the registry.
Microsoft documents both routes for the
[Azure OpenAI v1 API](https://learn.microsoft.com/en-us/azure/foundry/openai/api-version-lifecycle).

For an approved API-key deployment, the key does not belong in the registry, a
script, a notebook, a screenshot, or version control.

Use the secret-management method required by the institution. For a temporary
terminal session on macOS or Linux, enter the key without displaying it:

```bash
read -s AZURE_OPENAI_API_KEY
export AZURE_OPENAI_API_KEY
```

Press Enter after pasting the key. On Windows PowerShell:

```powershell
$secureKey = Read-Host "Azure API key" -AsSecureString
$env:AZURE_OPENAI_API_KEY = [System.Net.NetworkCredential]::new("", $secureKey).Password
```

The variable lasts for the current terminal session. There is no need to print
it to check that it was set.

Return to the terminal where the
[`llm-blog-repo`](https://github.com/marishkamehta/llm-blog-repo) environment is active.
If the registry was not created during the [pipeline
test](/blog/2026/mock-pipeline/), copy the example.

On macOS or Linux:

```bash
cp model-registry.yaml.example model-registry.yaml
```

On Windows PowerShell:

```powershell
Copy-Item model-registry.yaml.example model-registry.yaml
```

Open `model-registry.yaml` and replace the Azure placeholders with the values
provided for the deployment:

```yaml
azure-hosted:
  backend: azure
  base_url: https://YOUR-RESOURCE-NAME.openai.azure.com/openai/v1
  served_name: YOUR_DEPLOYMENT_NAME
  key_env: AZURE_OPENAI_API_KEY
```

`key_env` names the environment variable containing the API key; it does not
contain the key itself. `base_url` identifies the Azure resource, and
`served_name` is the deployment name supplied by its owner.

## One non-study request checks the connection

The smoke test sends “Say hello in three words.” It contains no study material,
but it does consume quota and may be billed. After the deployment owner has
authorized that request, run:

```bash
python smokes/smoke_chat.py --model azure-hosted
```

A successful result should name `azure-hosted`, contain a short model response,
and show request and response metadata. The pipeline redacts the authorization
value before saving the request. It also records sanitized response headers,
the service request ID, and any rate-limit headers returned by the deployment.

An unsuccessful request often identifies which part of the setup needs to be
checked:

- `401` points to the credential or its permissions;
- `404` points to the base URL or deployment name;
- `429` means that a request or token rate limit was reached; and
- a filter error means that the service did not return an ordinary model
  response.

Compare an error with the deployment information before sending the request
again. The smoke-test client does not retry automatically, so every diagnostic
request remains visible.

A response confirms that the pipeline can reach the deployment and save what it
returns. The behavioral demonstration tests the task itself.

## Preserve the hosted environment with the responses

The run record should include:

- the deployment name and underlying model version;
- the deployment type and processing location;
- a sanitized copy of the registry entry;
- the authentication method, but never the credential;
- the rate-limit and quota information;
- the content-filter configuration;
- the generation settings sent with each request;
- request IDs, timestamps, errors, rate-limit headers, and token usage; and
- the relevant governance approval and cost controls.

These records distinguish a model response from a request blocked by filtering,
rejected by authentication, or limited by quota.

## Ask an agent to check an existing Azure deployment

An agent can help connect a deployment that already exists. The prompt below
keeps resource creation, credentials, study materials, and repeated paid calls
outside its authority.

```text
I have downloaded and tested llm-blog-repo with its mock
backend. I have access to an existing institutionally approved Azure model
deployment.

Inspect the pipeline files and the non-secret deployment information I provide.
Before changing anything, identify what is still needed from this list:

- the complete Azure OpenAI v1 base URL;
- the deployment name used in the model field;
- the underlying model name and version;
- the deployment type and processing location;
- the approved authentication method;
- rate limits and quota;
- content-filter settings;
- data-governance restrictions; and
- the authorized billing project or cost center.

Do not ask me to paste a key into chat, a file, or a command that will display
it. Do not create or modify an Azure resource, deployment, role assignment,
filter, quota, or billing setting. Do not send study materials.

After I confirm the configuration and authorize one smoke-test request, add a
sanitized entry to model-registry.yaml, verify that the key is read from the
approved environment variable, and run only the non-study smoke test. Report
the command, HTTP result, deployment metadata returned by the service, request
ID, rate-limit headers, token usage, and any error. Stop after that request
unless I explicitly approve further paid calls.
```

A successful smoke test confirms that the pipeline can reach the model and save
its response. A behavioral experiment must also vary a condition, repeat the
procedure, and connect each response to the trial that produced it.

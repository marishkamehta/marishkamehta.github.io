_Studying LLM Behavior · Model setup_

After testing the pipeline with the mock backend, the next step is to connect a
real model. Ollama downloads and runs a model on the local computer, then
provides an API that the pipeline can call.

The setup below uses a locally downloaded model. Ollama also offers cloud
models, so the application name alone no longer establishes where a model ran.
When prompts or responses must remain local, cloud features should be disabled
and that setting recorded. Ollama describes its cloud models in the
[cloud documentation](https://docs.ollama.com/cloud) and explains how to
disable cloud features in its [FAQ](https://docs.ollama.com/faq).

## Install Ollama

Ollama provides installers for Windows, macOS, and Linux through its
[official quickstart](https://docs.ollama.com/quickstart). More detailed
instructions are available for
[Windows](https://docs.ollama.com/windows),
[macOS](https://docs.ollama.com/macos), and
[Linux](https://docs.ollama.com/linux).

After installation, open a new terminal and run the command below. The Ollama
commands used on this page are the same on Windows, macOS, and Linux:

```bash
ollama -v
```

The command should return the installed Ollama version. If the command is not
recognized, close and reopen the terminal.

On Windows and macOS, opening the Ollama application normally starts the local
service. A Linux installation may run it as a system service. If Ollama was
installed manually and is not already running, start it in a separate terminal:

```bash
ollama serve
```

Leave that terminal open during the checks below. By default, the pipeline will
reach the service at `http://localhost:11434`. In this address, `localhost`
means the same computer on which the pipeline is running.

## Choose a model the computer can support

For this check, select a model that fits the available computer. This is a setup
decision, not a substitute for choosing the model required by the research
question. Replacing that model with a smaller one changes the object being
studied.

The commands below use the 3-billion-parameter Qwen 2.5 instruction model:

```bash
ollama pull qwen2.5:3b
```

This model is smaller than many commonly used instruction models, but it is not
guaranteed to fit or run quickly on every computer. The download also requires
several gigabytes of storage. The
[Ollama model library](https://ollama.com/library) lists other models and sizes.

Once it finishes, list the locally available models:

```bash
ollama ls
```

Copy the model name exactly as shown by `ollama ls`. Then retrieve the model
information:

```bash
curl http://localhost:11434/api/tags
```

The command returns a list of the models on the computer. The section for this
model will include two fields like these:

```json
{
  "name": "qwen2.5:3b",
  "digest": "a long string of letters and numbers"
}
```

The **digest** identifies the downloaded Ollama package more precisely than a
name such as `qwen2.5:3b`, which may remain unchanged after the package is
updated. Record both values. A broad label such as “Qwen” or “Qwen 2.5” does
not identify the model precisely enough.

The Ollama setup and the later vLLM demonstration use models from the same Qwen
2.5 3B family, but they should not be treated as identical deployments. Ollama
may use quantized weights or format the chat differently. Record these
differences when comparing results across the two setups.

Before connecting the pipeline, ask the model for one response directly:

```bash
ollama run qwen2.5:3b "Reply with only the word READY."
```

The wording may not be exactly `READY`. At this stage, the command only shows
that the model can generate text. It is not an experimental trial.

Downloading and loading are two different steps. `ollama pull` saves the model
files to the computer's storage. When `ollama run` is called, Ollama loads that
model into the available CPU or GPU memory so that it can generate a response.
Ollama usually keeps the model in memory for a period after the response, which
allows `ollama ps` to report how it was loaded.

## Confirm how the local model is using the computer

Immediately after the test response, run:

```bash
ollama ps
```

The output reports whether the model is using the CPU, GPU, or both. It also
reports the context currently allocated to the model. A model running on the
CPU has not necessarily failed, but collecting many responses may take much
longer. Ollama explains the processor values in its
[FAQ](https://docs.ollama.com/faq).

If the study requires local-only operation, disable Ollama's cloud features
before data collection and preserve that setting with the study documentation.
Do not infer that a model ran locally from the application name alone.

## Connect the pipeline to Ollama

Return to the terminal where the
[`llm-blog-repo`](https://github.com/marishkamehta/llm-blog-repo) environment is active.
From that folder, copy the example model registry. On macOS or Linux, run:

```bash
cp model-registry.yaml.example model-registry.yaml
```

On Windows PowerShell, run:

```powershell
Copy-Item model-registry.yaml.example model-registry.yaml
```

Open `model-registry.yaml` in a text editor and set its Ollama entry to:

```yaml
ollama-local:
  backend: ollama
  base_url: http://localhost:11434/v1
  served_name: qwen2.5:3b
```

`ollama-local` is the name used by the experiment. `base_url` points to
Ollama's local chat-completions endpoint, and `served_name` must match the name
returned by `ollama ls`. Ollama documents the `/v1` route as part of its
[OpenAI compatibility API](https://docs.ollama.com/api/openai-compatibility);
the phrase describes the request format, not who developed or hosts the model.

The working registry is ignored by Git because other entries may contain
private endpoints. Preserve a sanitized copy of this entry with the study
record.

## Send the first pipeline request to the model

With Ollama running and the pipeline environment active, run:

```bash
python smokes/smoke_chat.py --model ollama-local
```

The output should name `ollama-local`, contain a generated reply, and include
response metadata. Unlike `MOCK_RESPONSE`, the reply is produced by a
generative model and does not need to match an example word for word.

If the connection is refused, check that the Ollama application or
`ollama serve` is still running. If the model is not found, compare
`served_name` with `ollama ls`, including the text after the colon.

A generated response confirms that the pipeline can reach Ollama and save what
it returns. Task understanding is tested later with the behavioral
demonstration.

## Session length changes the memory required

The [pipeline test](/blog/2026/mock-pipeline/) introduced the growing trajectory: each
new trial can include the instructions and earlier turns from the same session.
The input therefore becomes longer as the session proceeds, and the longest
valid trajectory must fit within the model's context length.

Ollama's context defaults depend on the available memory. Increasing the
context also increases memory use
([Ollama context-length documentation](https://docs.ollama.com/context-length)).
For a short smoke test, the default is sufficient. Before collecting data,
estimate the longest possible trajectory, leave room for the response, and set
the context length before freezing the protocol.

A larger context is not automatically better. It can make the study slower or
cause a model that fit on the GPU to move partly into system memory. Record the
allocated context shown by `ollama ps`, and do not change it midway through a
run without documenting the change.

## Preserve the environment used to generate the responses

The local setup still has to be documented. Before collecting data, preserve:

- the output of `ollama -v`;
- the exact model name, identifier, and full digest;
- the processor allocation and context length from `ollama ps`;
- the sanitized registry entry used by the study;
- the generation settings;
- the operating system and available CPU, RAM, and GPU memory; and
- whether Ollama cloud features were enabled or disabled.

Running the model locally removes some provider-side uncertainty, but it does
not make the environment self-documenting. The Ollama version, model file,
quantization, drivers, and hardware are all part of the conditions under which
the responses were produced.

## Ask an agent to help with the local setup

After the pipeline passes its offline mock tests, an agent can inspect the
computer and help connect Ollama. Installing software and downloading a model
change the computer and may use substantial disk space, so the prompt requires
approval before either action.

```text
I have downloaded and tested llm-blog-repo with its mock
backend. I now want to connect it to a model that runs locally through
Ollama.

First inspect, without changing anything:

- my operating system, CPU, RAM, GPU and GPU memory, and free disk space;
- whether Ollama is installed and running;
- which Ollama models are already downloaded; and
- the pipeline's model-registry example and smoke test.

Explain what you find in plain language. Recommend a small instruction-tuned
model that is likely to fit, but do not install Ollama or download a model
until I approve the exact action and expected download size. Do not select a
cloud model. If local-only operation is required, verify that Ollama cloud
features are disabled.

After approval, use the official Ollama instructions for my operating system.
Record the Ollama version, exact model name, identifier, digest, processor
split, and allocated context length. Add the model to model-registry.yaml
without changing the experimental task, then run the pipeline smoke test. Do
not run a full experiment or incur paid charges. Report every command used,
any files changed, and the complete smoke-test result.
```

A successful smoke test confirms that the pipeline can reach the model and save
its response. A behavioral experiment must also vary a condition, repeat the
procedure, and connect each response to the trial that produced it.
